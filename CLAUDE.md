# Project rules

- All code must be in English: source code, comments, identifiers, UI copy/strings, commit messages, and any data files (`public/data/products.json`, `public/data/reviews.json`). Do not introduce non-English text anywhere in the repo, even though this is a POC for a Ukrainian-market product.

# Stack & architecture

- React 19 + Vite: function components with hooks (`useState`/`useMemo`/`useEffect`/`useRef`) for all state — not classes, not a global store (Redux/Zustand/etc.), everything lives in `App` and is passed down as props, same as the app's previous signal-based architecture. TypeScript strict mode throughout.
- `public/data/products.json` / `reviews.json`: the first 5 ids per category (`<slug>-01`..`<slug>-05`) are hand-written originals. The rest (up to 300 total) are procedurally generated by `scripts/generate-catalog.js`, which is deterministic and idempotent — it always rebuilds the generated set from just those 30 originals, so rerunning it after editing an original or a template regenerates the whole catalog consistently. Never hand-edit a generated entry directly; edit the originals and/or the generator, then rerun it.
- Products have no `color`/`colorHex` field, no color filter, and no color words anywhere in names/descriptions/tags/reviews — every product icon is the same plain green SVG (not a real photo), so a color attribute would just be misleading noise with nothing on screen to back it up. Don't reintroduce color as a product attribute.
- Secrets: `.env` (gitignored) holds `VITE_GROQ_API_KEY`/`VITE_GROQ_MODEL`, loaded natively by Vite and read in code via `import.meta.env`. Only `VITE_`-prefixed vars are exposed to client code, by design — there's no generator script or committed environment file to keep in sync; a fresh clone just needs its own `.env`.
- Groq's model catalog changes over time — if `aiSearch()` in `src/lib/groq.ts` starts failing with a `model_not_found`/404, the configured `VITE_GROQ_MODEL` has likely been retired; check `https://console.groq.com/docs/models` (or `GET /openai/v1/models` with the actual key) for what's currently live. Also: the full product catalog (up to 300 items) is far too large to send to Groq in one request on typical free-tier rate limits, so `groq.ts` pre-narrows it with `localHeuristicSearch` to `MAX_CANDIDATES` (25) before ever calling the API — don't revert to sending the whole catalog.
- Tests: `npm test` runs unit specs (`vitest run`), component tests use `@testing-library/react`. `npm run eval:search` is a retrieval-accuracy regression check for the synonym-expansion search — if the catalog data or concept groups change meaningfully, rerun it and update its ground-truth ids if it fails.
- When changing UI, verify against an actual running instance (dev server + a headless-browser screenshot + console-error check) — a passing build/test suite alone doesn't confirm the UI actually looks or behaves right.
- The guided tour (`src/lib/tour.ts`, `driver.js`) is owned by `App`, not by a leaf component — its last few steps run a live demo (fills the search box, runs a real search, opens a card) and need App-level state (`onSearch`, `filteredProducts`, `selectedId`). Because the tour driver instance is created once (via a `useRef`, lazily on first `startTour()` call) and its callbacks are captured at that point, those callbacks read through a small `latestRef` (updated every render) rather than closing over stale state — the React equivalent of Angular's stable `this`. A step with a custom `popover.onNextClick` must call `opts.driver.moveNext()` itself — providing that hook fully replaces the default advance behavior. Cleanup (clearing the demo query, closing the modal) lives in the driver `Config`'s `onDestroyStarted`, which fires however the tour ends (Done, the × button, Escape, overlay click) — but per driver.js's own internals, that hook only *asks* to destroy; you must call `opts.driver.destroy()` yourself inside it or the tour never actually closes. **`driver.destroy()` called directly (e.g. from outside the tour, like the postMessage bridge's dismiss handler) bypasses `onDestroyStarted` entirely** (its public `destroy` is the "force" path) — so any external code that ends the tour must replicate `App`'s reset logic (`resetTourDemo()`) itself before calling `destroy()`, or the demo state/`poc-tour-status` broadcast never fires.
- This app is designed to be embedded in a host page's `<iframe>` — `src/lib/post-message.ts` is a deliberately small subset of a larger shared postMessage contract, hand-picked for what this app actually has (no file upload/media preview, no client-side routing, so those message types were left out). It sends `poc-frame-ready`/`poc-resize-iframe` (wired in `App` via `src/lib/iframe-resize.ts`'s `ResizeObserver`), `poc-tour-status` and `poc-scroll-into-view` (from the guided tour), and `poc-modal` (from `ProductModal`'s mount/unmount `useEffect`). It listens for `ask-for-height`, `poc-host-ready`, and `poc-dismiss` (host-forwarded click/Escape on its own dim, for whichever overlay — tour or modal — is currently open; both listen independently, same as native Escape already behaves when both happen to be open at once). All of it is a no-op when the app isn't actually embedded (`isEmbedded()` checks `window.parent !== window`), so it's silent and harmless in normal dev/standalone use.
