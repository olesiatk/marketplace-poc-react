# Project rules

- All code must be in English: source code, comments, identifiers, UI copy/strings, commit messages, and any data files (`public/data/products.json`, `public/data/reviews.json`). Do not introduce non-English text anywhere in the repo, even though this is a POC for a Ukrainian-market product.

# Stack & architecture

- React 19 + Vite: function components with hooks (`useState`/`useMemo`/`useEffect`/`useRef`) for all state — not classes, not a global store (Redux/Zustand/etc.), everything lives in `src/App.tsx` and is passed down as props, same as the app's previous signal-based architecture. TypeScript strict mode throughout. `App.tsx` itself is a thin `<InstantSearch>` provider wrapper around an inner `AppShell` — React Context only reaches descendants, so the component that calls `react-instantsearch`'s hooks (`useSearchBox`, `useHits`, etc.) has to render *below* the provider, not alongside it; `AppShell` is where all the real state/orchestration described below actually lives.
- `public/data/products.json` / `reviews.json`: the first 5 ids per category (`<slug>-01`..`<slug>-05`) are hand-written originals. The rest (up to 300 total) are procedurally generated by `scripts/generate-catalog.js`, which is deterministic and idempotent — it always rebuilds the generated set from just those 30 originals, so rerunning it after editing an original or a template regenerates the whole catalog consistently. Never hand-edit a generated entry directly; edit the originals and/or the generator, then rerun it.
- Products have no `color`/`colorHex` field, no color filter, and no color words anywhere in names/descriptions/tags/reviews — every product icon is the same plain green SVG (not a real photo), so a color attribute would just be misleading noise with nothing on screen to back it up. Don't reintroduce color as a product attribute.
- Secrets: `.env` (gitignored) holds `VITE_ALGOLIA_APPLICATION_ID`/`VITE_ALGOLIA_SEARCH_API_KEY` (client-safe, read via `import.meta.env` in `src/lib/algolia.ts`) and `ALGOLIA_WRITE_API_KEY` (deliberately **not** `VITE_`-prefixed — only read server-side by `scripts/index-algolia.ts`, never bundled to the client). Only `VITE_`-prefixed vars are exposed to client code, by design — there's no generator script or committed environment file to keep in sync; a fresh clone just needs its own `.env`.
- Search is Algolia (`algoliasearch/lite` + `react-instantsearch`), index `marketplace-poc-products`, built by `npm run index:products` (`scripts/index-algolia.ts`). That script merges `products.json` + `reviews.json` into Algolia records (reviews embedded per-product, so the client never fetches `reviews.json` at runtime — only `products.json`, and only to build the search-box autocomplete vocabulary), configures faceting (`category`/`materialFacets`/`roomFacets`/`price` — the facet fields are split from the comma/paren-separated `material`/`room` strings, since Algolia facets want discrete values), and pushes `CONCEPT_GROUPS` from `src/lib/synonyms.ts` as Algolia synonym sets — that's what makes a query like "cosy" still find products only ever described as "cozy"/"comfortable". Re-run `index:products` whenever the catalog or `CONCEPT_GROUPS` changes meaningfully. `AppShell` (in `App.tsx`) is the primary place that talks to `react-instantsearch` — `FiltersBar`/`ProductGrid` stay engine-agnostic and receive plain props, same as before the Algolia migration; `ProductCard`/`ProductModal` are exceptions, since they render Algolia's own `<Highlight>`/`<Snippet>` components directly against the hit they're given, and `Hero` renders `<PoweredBy>` next to the search bar — required by Algolia's free-tier terms, not optional branding, so don't remove it even though the rest of Hero stays plain-props.
- Tests: `npm test` runs unit specs (`vitest run`), component tests use `@testing-library/react`.
- When changing UI, verify against an actual running instance (dev server + a headless-browser screenshot + console-error check) — a passing build/test suite alone doesn't confirm the UI actually looks or behaves right.
- The guided tour (`src/lib/tour.ts`, `driver.js`) is owned by `AppShell`, not by a leaf component — its last few steps run a live demo (fills the search box, runs a real search, opens a card) and need that top-level state (`onSearch`, the current `hits` from `useHits()`, `selectedProduct`). Because the tour driver instance is created once (via a `useRef`, lazily on first `startTour()` call) and its callbacks are captured at that point, those callbacks read through a small `latestRef` (updated every render) rather than closing over stale state — the React equivalent of Angular's stable `this`. A step with a custom `popover.onNextClick` must call `opts.driver.moveNext()` itself — providing that hook fully replaces the default advance behavior. Cleanup (clearing the demo query, closing the modal) lives in the driver `Config`'s `onDestroyStarted`, which fires however the tour ends (Done, the × button, Escape, overlay click) — but per driver.js's own internals, that hook only *asks* to destroy; you must call `opts.driver.destroy()` yourself inside it or the tour never actually closes. **`driver.destroy()` called directly (e.g. from outside the tour, like the postMessage bridge's dismiss handler) bypasses `onDestroyStarted` entirely** (its public `destroy` is the "force" path) — so any external code that ends the tour must replicate `AppShell`'s reset logic (`resetTourDemo()`) itself before calling `destroy()`, or the demo state/`poc-tour-status` broadcast never fires.
- This app is designed to be embedded in a host page's `<iframe>` — `src/lib/post-message.ts` is a deliberately small subset of a larger shared postMessage contract, hand-picked for what this app actually has (no file upload/media preview, no client-side routing, so those message types were left out). It sends `poc-frame-ready`/`poc-resize-iframe` (wired in `AppShell` via `src/lib/iframe-resize.ts`'s `ResizeObserver`), `poc-tour-status` and `poc-scroll-into-view` (from the guided tour), and `poc-modal` (from `ProductModal`'s mount/unmount `useEffect`). It listens for `ask-for-height`, `poc-host-ready`, and `poc-dismiss` (host-forwarded click/Escape on its own dim, for whichever overlay — tour or modal — is currently open; both listen independently, same as native Escape already behaves when both happen to be open at once). All of it is a no-op when the app isn't actually embedded (`isEmbedded()` checks `window.parent !== window`), so it's silent and harmless in normal dev/standalone use.
